# OpenCode Pocket: встроенный OpenCode (design)

Дата: 2026-11-06. Статус: черновик на утверждение.

## Зачем

Сейчас Pocket — тонкий клиент к серверу OpenCode, который живёт в Termux.
Это удобно для отладки, но как продукт плохо: Termux должен висеть, сервер
надо поднимать руками, настройки и сессии лежат в чужом каталоге, а лимит
бесплатных моделей приходится обходить сменой VPN.

Нужно приложение, которое само содержит настоящий OpenCode v2, полностью
управляет им из UI и не зависит от Termux, ADB или root.

## Цели

1. OpenCode-сервер запускается из APK автоматически, без Termux и root.
2. UI сам подключается к нему; режим внешнего сервера остаётся для отладки.
3. Сессии, настройки, скилы, MCP и логи живут в приватном каталоге
   приложения и управляются из UI.
4. Рабочий каталог — обычная папка на телефоне (`/sdcard/OpenCode`),
   с полным доступом к файлам.
5. Провайдеры и ключи настраиваются в приложении: свои ключи
   Anthropic / OpenAI / OpenRouter / OpenAI-совместимые, аккаунт OpenCode.
6. Состояние чата, выбранная сессия, черновик и транскрипт переживают
   перезапуск и поворот экрана (уже сделано, сохраняем).
7. Долгие ходы не прерываются, когда приложение уходит в фон.

## Не-цели

- Переписывать OpenCode на Kotlin.
- Поддерживать x86/armeabi-v7a: только arm64-v8a.
- Публикация в Google Play (side-load).
- Локальные LLM/инференс на устройстве в этой итерации.
- Свой веб-клиент вместо текущего Compose UI.

## Анти-цели

- Обычная работа требует Termux, ADB или root.
- Скрытые сетевые запросы куда-либо, кроме выбранного провайдера.
- Потеря существующих сессий и настроек при миграции.

## Ограничения и факты

- `opencode` — нативный Android ARM64 ELF (собран NDK), 170 МБ, зависит
  только от `libc/libm/libdl`. Проверено: запускается с отдельными
  `HOME`/XDG-каталогами, сам генерирует пароль, отдаёт API.
- Android разрешает exec только из `nativeLibraryDir`, поэтому бинарник
  кладём как `jniLibs/arm64-v8a/libocserver.so` и включаем
  `extractNativeLibs`/`useLegacyPackaging`.
- APK вырастет примерно до 180 МБ.
- Главный риск: JIT. Bun/JSC может требовать исполняемую память, которую
  Android 10+ запрещает приложениям с targetSdk ≥ 29. Сначала спайк;
  запасной путь — targetSdk 28 (домен `untrusted_app_27`), что заодно
  даёт legacy-доступ к `/sdcard`.
- Shell в Android — toybox (`/system/bin/sh`), нет git/node. В MVP
  обходимся системными утилитами; busybox/git можно добавить позже.
- Android убивает фоновые процессы: сервер и активный ход прикрываем
  foreground-сервисом с уведомлением.

## Архитектура

### ServerManager

- Выбирает свободный порт (по умолчанию 4096), готовит окружение:
  `HOME`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `TMPDIR`,
  `PATH=/system/bin:/system/xbin`.
- Перед стартом пишет свой пароль в `config/opencode/service.json`,
  чтобы UI не парсил stdout.
- Запускает `nativeLibraryDir/libocserver.so serve --hostname 127.0.0.1
  --port <port>` с рабочим каталогом workspace.
- Пишет stdout/stderr в кольцевой буфер и файл `logs/server.log`.
- Ждёт `/api/info` до 30 с, отдаёт `baseUrl` и пароль во ViewModel.
- Умеет stop/restart, статус и хвост лога для экрана «Связь».

### Режимы

- `embedded` — по умолчанию: сервер поднимает само приложение.
- `external` — текущий режим (URL + пароль), нужен для отладки и для
  случая, когда сервер уже крутится на компьютере.

Настройки хранят режим; при `embedded` поля URL/пароля скрыты.

### Каталоги приложения

```
files/opencode/
  home/.config/opencode/{config.json,service.json,skills/...}
  home/.local/share/opencode/{opencode.db,log,...}
  home/.cache/opencode/
  logs/server.log
```

Рабочий каталог — `/sdcard/OpenCode` (настраивается). Доступ к общим
файлам:
- вариант A: `targetSdk 28` + `WRITE_EXTERNAL_STORAGE` (просто, но старый
  targetSdk);
- вариант B: targetSdk 35 + `MANAGE_EXTERNAL_STORAGE` (пользователь
  выдаёт «Доступ ко всем файлам»).
Решение: спайк прошёл на targetSdk 35 (сервер запустился и ответил
`/api/info`), поэтому берём вариант B.

### Провайдеры и авторизация

- Экран «Провайдеры»: список интеграций, добавление ключа, проверка,
  выбор модели по умолчанию.
- Хранение — в `auth.json` каталога OpenCode (или через подкоманду
  `auth import`), плюс зеркало в зашифрованных настройках Pocket, чтобы
  не потерять при переустановке (экспорт).
- Бесплатные модели OpenCode остаются с лимитом аккаунта; UI честно
  показывает остаток/ошибку и предлагает добавить свой ключ.

### Скилы

- Экран «Скилы»: глобальные (`config/opencode/skills`) и проектные
  (`.opencode/skills` в workspace).
- Просмотр, создание, редактирование `SKILL.md`, включение/выключение.
- После изменений — reload сервера (если есть endpoint) или рестарт.

### Фоновый режим

- Foreground service `:server` держит процесс OpenCode и показывает
  уведомление «OpenCode работает» с кнопкой «Стоп».
- Запускается при старте приложения; останавливается пользователем или
  при явном выходе.

### UI

- Первый запуск: выбор workspace, выдача доступа к файлам, экран
  «Поднимаю OpenCode…» с прогрессом/логом.
- «Связь»: режим, статус сервера, порт, версия, лог, рестарт, экспорт
  логов, переключение на внешний сервер.
- «Провайдеры», «Скилы», «Рабочий каталог» — новые экраны.
- Исправления из тестов: дубль заголовка external-поля, «Своё значение»
  не показывает выбранный пресет, кнопки формы после клавиатуры.

## Этапы

1. **Спайк (throwaway).** Собрать APK с бинарником, запустить сервер,
   проверить `/api/info` и JIT. Результат: **пройден** на targetSdk 35 —
   сервер поднялся, `/api/info`, `/api/session` и `/api/model` отвечают,
   БД создаётся в приватном каталоге. Ограничение JIT не проявилось.
2. **MVP.** ServerManager + foreground service + авто-подключение,
   режим external, экран логов, workspace.
3. **Провайдеры.** Экран ключей, импорт/экспорт, выбор модели.
4. **Скилы и сессии.** Управление скилами, миграция сессий из Termux,
   архив/удаление.
5. **Полировка.** Фиксы формы/IME, README, версия, проверка поворота
   и восстановления после kill.

## Риски

| Риск | Что делаем |
|---|---|
| JIT/execmem запрещён | targetSdk 28 или отключение JIT у JSC |
| 170 МБ в APK и на сборке | бинарник не в git, кэш на билд-сервере |
| Android убивает сервер | foreground service |
| Нет git/node в shell | MVP без них, позже busybox |
| Потеря сессий | экспорт/импорт, миграция из Termux |
| Обновление OpenCode | замена бинарника в APK, версия в настройках |

## Что решено, что оставляем строителю

Решено: вариант «OpenCode внутри APK», arm64, приватный HOME, workspace
на `/sdcard`, внешний режим сохраняем.

Оставляем: точный способ выдачи доступа к файлам (A/B после спайка),
формат экрана провайдеров, нужен ли root-shell, набор bundled-утилит.

## Решения по вопросам независимой проверки

1. **Миграция.** Пережить должны: сессии (история), настройки OpenCode
   (`config.json`), скилы и ключи провайдеров. Проектные файлы остаются
   там, где пользователь их держит; в MVP их не переносим. Перенос из
   Termux — разовый, вручную: пользователь копирует каталоги
   `~/.local/share/opencode` и `~/.config/opencode` в `/sdcard`, приложение
   импортирует их и переписывает `directory` старых сессий на новый
   workspace (старый путь сохраняется в истории, если файлов нет).
   Это этап 4, но без потери данных: до миграции внешний режим остаётся
   рабочим.
2. **Обновление существующей установки.** После установки новой версии
   приложение не переключается само: оно показывает предложение
   «Перенести Termux → встроенный сервер». Пока пользователь не подтвердил,
   работает прежний внешний URL/пароль и текущая сессия. После переноса
   режим `embedded` становится основным, а внешний остаётся в настройках.
3. **Аккаунт OpenCode.** В MVP — импорт существующего credential
   (`auth export` / файл) и вставка токена; device-flow с кодом и
   браузером добавляем после MVP. Квоту отдельным экраном не рисуем:
   показываем ошибку провайдера и кнопку «Добавить свой ключ».
4. **Жизненный цикл.** Сервер и уведомление живут в foreground-сервисе,
   пока пользователь не нажмёт «Стоп» в уведомлении или в приложении.
   Свайп из recents сервер не убивает; после перезагрузки автозапуска нет.
   «Явный выход» — только кнопка «Стоп». Сервис отдельного процесса не
   требует: URL/пароль/статус/лог доступны через общий `ServerManager`
   и файл лога.
5. **Долговечность ключей.** Гарантия — ручной экспорт/импорт
   зашифрованного файла в выбранное пользователем место (SAF). Автобэкап
   в облако и восстановление после uninstall без файла не обещаем.
6. **MCP.** В этой итерации явно вне scope. Экран скилов и провайдеров
   делаем, MCP — следующая итерация.
